# Centralize generation of plugin distribution artifacts

Design spec for GitHub issue #33.

## Problem

The repository already generates some plugin distribution payloads (`skills/`, `vendor/`, `bin/cities2-mcp-launcher.js`, `vendor/run_server.py`) through `cities2_mcp.plugin_packages`, but the platform-specific metadata files (`plugin.json`, `.mcp.json`, `README.md`, `marketplace.json`, `mcp_config.json`) are still hand-maintained across three logical platforms. Shared values such as version, name, description, author, repository and privacy URLs, keywords, skill paths, MCP launch commands, marketplace entries, and README boilerplate are repeated by hand and only partially guarded by tests, so they drift.

## Goal

Extend `cities2_mcp.plugin_packages` so that `sync` regenerates every intended plugin distribution metadata file from a single canonical source, and `check` fails when any Claude, Codex, or Antigravity metadata artifact drifts — while preserving intentional platform-specific config and launch behavior.

## Scope decisions (settled during brainstorming)

- **Full generation.** Each metadata file is generated 100% from a canonical model plus per-platform definitions. `sync` rewrites the whole file; `check` compares the whole file. Platform-specific config is encoded in the builder for that platform.
- **Python module as canonical source.** Shared values and per-platform builders live in a new module `cities2_mcp/plugin_metadata.py`. Artifacts are built as Python dicts (`json.dumps`) or string templates. No new dependency. Version is sourced from `cities2_mcp.__version__`.
- **Plugin artifacts only.** The generator reads `cities2_mcp.__version__` as canonical and propagates it into the plugin distribution artifacts and marketplace files listed below. `pyproject.toml` and `server.json` keep their current handling (already version-checked in `tests/test_packaging.py`).
- **Out of scope:** version *bumping* stays manual (per `AGENTS.md`, version numbers are only changed when a human directs it). The generator never bumps a version; it only propagates the existing `__version__`.

## Current state (for reference)

Canonical sources today:

- root `skills/` — the five user-facing skills (`cities2-knowledge`, `cities2-modding`, `cities2-mod-review`, `cities2-mod-debugging`, `cities2-mod-release`).
- root `cities2_mcp/` — the Python package, vendored into each distro.
- `cities2_mcp/__init__.py` → `__version__ = "0.1.9"`.

Already generated by `plugin_packages.py` (unchanged by this work): `skills/`, `vendor/` (copy of `cities2_mcp/` plus generated `run_server.py`), `bin/cities2-mcp-launcher.js`, across the two physical package roots `integrations/anthropic/claude-plugin` and `plugins/cities2-mcp`.

The Codex and Antigravity distributions share the single directory `plugins/cities2-mcp`.

## Canonical model: `cities2_mcp/plugin_metadata.py`

A new module that is the single source of truth for shared plugin identity and per-platform artifact content.

### Shared constants

- `NAME = "cities2-mcp"`
- `DISPLAY_NAME = "Cities2 MCP and Modding Toolkit"`
- `AUTHOR = {"name": "mayor-modder", "url": "https://github.com/mayor-modder"}`
- `REPO_URL = "https://github.com/mayor-modder/Cities2-MCP"` (also homepage)
- `LICENSE = "MIT"`
- `PRIVACY_URL = "https://github.com/mayor-modder/Cities2-MCP/blob/main/PRIVACY.md"`
- `TERMS_URL = "https://github.com/mayor-modder/Cities2-MCP#license"`
- `KEYWORDS = ["cities-skylines-ii", "mcp", "modding", "gameplay", "agent-skills"]`
- `SKILL_NAMES` — the five skill names (single source; `plugin_packages.py` and `agent_assets.py` import this instead of redefining it).
- Per-platform descriptions:
  - Claude: `"Cities2 MCP and Modding Toolkit for Claude."`
  - Codex: `"Cities2 MCP and Modding Toolkit for Codex."`
  - Antigravity: `"Cities: Skylines II knowledge and modding tools for AI agents."`
- Marketplace-only values (not derivable from the above):
  - `CLAUDE_MARKETPLACE_DESCRIPTION = "Claude plugin marketplace for Cities2 MCP and Modding Toolkit."` (distinct from the per-plugin Claude description).
  - Marketplace owner == `AUTHOR` (the Claude marketplace `owner` block reuses the canonical author).
- Version is imported: `from cities2_mcp import __version__ as VERSION` (no circular import — `__init__.py` does not import this module).

### Platform-specific structures (kept verbatim)

- `CLAUDE_USER_CONFIG` — the `userConfig` dict (`trusted_workspace`, `mods_dir`, `game_dir`, `locale_cok`) with current titles/descriptions.
- `CODEX_INTERFACE` — the `interface` dict (`displayName`, `shortDescription`, `longDescription`, `developerName`, `category`, `capabilities`, `websiteURL`, `privacyPolicyURL`, `termsOfServiceURL`, `defaultPrompt`, `brandColor`, `screenshots`).
- `ANTIGRAVITY_BOOTSTRAP_JS` — the single-line inline node `-e` bootstrap string (currently in `mcp_config.json`), stored as a module constant like the existing `LAUNCHER_TEXT`. The bootstrap text uses only single quotes, so it is stored as a normal Python string; `json.dumps` performs all JSON escaping when it is serialized.
- `CLAUDE_MARKETPLACE_ENTRY` — the Claude marketplace plugin entry shape: `name=NAME`, `source="./integrations/anthropic/claude-plugin"`, `description=` the Claude per-platform description, `version=VERSION`, `author=AUTHOR`. The marketplace top-level uses `name=NAME`, `description=CLAUDE_MARKETPLACE_DESCRIPTION`, `owner=AUTHOR`.
- `CODEX_MARKETPLACE` — the Codex/Antigravity marketplace shape: top-level `interface={"displayName": DISPLAY_NAME}`, plugin entry with `name=NAME`, `source={"source": "local", "path": "./plugins/cities2-mcp"}`, `policy={"installation": "AVAILABLE", "authentication": "ON_INSTALL"}`, `category="Coding"`.

### Builder functions

Each builder returns the exact file content string. JSON builders construct a dict with keys in the order matching the current on-disk file (to minimize first-sync diff), then `return json.dumps(obj, indent=2, ensure_ascii=False) + "\n"`. README builders return a per-platform template string.

| Builder | Produces |
| --- | --- |
| `claude_plugin_json()` | Claude `.claude-plugin/plugin.json` |
| `claude_mcp_json()` | Claude `.mcp.json` |
| `claude_readme_md()` | Claude `README.md` |
| `claude_marketplace_json()` | root `.claude-plugin/marketplace.json` |
| `codex_plugin_json()` | Codex `.codex-plugin/plugin.json` |
| `codex_mcp_json()` | Codex `.mcp.json` |
| `codex_readme_md()` | Codex/shared `README.md` |
| `codex_marketplace_json()` | root `.agents/plugins/marketplace.json` |
| `antigravity_plugin_json()` | Antigravity `plugin.json` |
| `antigravity_mcp_config_json()` | Antigravity `mcp_config.json` |

`claude_marketplace_json` / `codex_marketplace_json` assemble the marketplace constants/structures above (`CLAUDE_MARKETPLACE_DESCRIPTION`, `CLAUDE_MARKETPLACE_ENTRY`, `CODEX_MARKETPLACE`) plus `VERSION`, so every literal in both marketplace files is traceable to the canonical model — the same way `plugin.json` content is.

Builders are pure functions of the module constants and the imported version. They do not read the filesystem, so generation is deterministic and does not require the corpus or skills to be present.

### README generation

Both READMEs are fully generated:

- Shared bits (skill list derived from `SKILL_NAMES`, repo URL) come from constants. The exact CLI commands are embedded verbatim in the templates: Claude = `claude plugin validate integrations/anthropic/claude-plugin --strict` (including `--strict` and the explicit package path); Codex = `codex plugin marketplace add mayor-modder/Cities2-MCP`. `test_repo_metadata_in_sync` enforces that the committed READMEs match these exactly.
- Codex's platform-specific prose (allowlist-blocked workflow tools, the `cities2-modding` template-copy fallback) is carried in its template — preserved verbatim in meaning, but authored as single-line paragraphs per `AGENTS.md` (markdown prose is one logical line per paragraph), reflowed from the current hard-wrapped source so the generated artifact passes the repo's markdown style gate and matches the Claude README style.
- Each generated markdown file starts with an HTML-comment marker: `<!-- Generated by cities2_mcp.plugin_packages; edit canonical sources in cities2_mcp/plugin_metadata.py, not this file. -->`. JSON cannot carry comments, so the contributor docs are authoritative for those.

## Generator integration: `cities2_mcp/plugin_packages.py`

### Metadata registry grouped by package root

Add a mapping from each package root to its list of generated metadata files, each entry a `(repo_relative_path, builder)` pair. Repo-root marketplace files are associated with their owning group:

- Claude group (`integrations/anthropic/claude-plugin`):
  - `integrations/anthropic/claude-plugin/.claude-plugin/plugin.json` → `claude_plugin_json`
  - `integrations/anthropic/claude-plugin/.mcp.json` → `claude_mcp_json`
  - `integrations/anthropic/claude-plugin/README.md` → `claude_readme_md`
  - `.claude-plugin/marketplace.json` → `claude_marketplace_json`
- Codex + Antigravity group (`plugins/cities2-mcp`):
  - `plugins/cities2-mcp/.codex-plugin/plugin.json` → `codex_plugin_json`
  - `plugins/cities2-mcp/.mcp.json` → `codex_mcp_json`
  - `plugins/cities2-mcp/README.md` → `codex_readme_md`
  - `.agents/plugins/marketplace.json` → `codex_marketplace_json`
  - `plugins/cities2-mcp/plugin.json` → `antigravity_plugin_json`
  - `plugins/cities2-mcp/mcp_config.json` → `antigravity_mcp_config_json`

Grouping by package root means metadata for a root is only generated when that root is in the `package_roots` passed to `sync_packages`/`check_packages`. This preserves the scoping behavior the existing unit tests rely on (they pass a single package root).

### sync / check passes

Extend the existing per-package-root loop in both functions. The metadata pass writes and compares **directly against the real (committed) tree** at `root / repo_relative_path` — it does **not** stage through the `TemporaryDirectory` `expected_root` / `_replace_payload` flow that the payload pass uses (builders are pure and ignore disk, so there is nothing to copy). `_write_payload`/`_replace_payload` are unchanged; the metadata pass is a new, direct compare-and-write step.

- `sync_packages`: after writing the tree payload for a root, iterate that root's metadata entries; for each, compute `builder()` and compare its text to the file at `root / repo_relative_path`. When content differs (or the file is missing), call `target.parent.mkdir(parents=True, exist_ok=True)`, write the builder output directly to that real path, and record the absolute path as changed.
- `check_packages`: after the tree comparison for a root, iterate that root's metadata entries; for each, compare `builder()` to the file at `root / repo_relative_path` and record the absolute path as stale when it differs or is missing.

**Line-ending handling (load-bearing on Windows).** Metadata comparison and writes use text (universal-newline) I/O, **not** byte I/O: read with `Path.read_text(encoding="utf-8")` and compare to `builder()` (a `str` ending in `"\n"`); write with `Path.write_text(builder(), encoding="utf-8")`. This differs from the existing tree-payload pass, which materializes both sides to disk and compares `read_bytes`. The repo's `.gitattributes` forces `eol=lf` only for `*.md` (not `*.json`) and `core.autocrlf=true`, so the JSON metadata files are checked out as CRLF on Windows. `read_text` decodes CRLF to `"\n"` (matching the builder), and `write_text` re-emits the platform newline so `sync` does not fight git's autocrlf — a `read_bytes`/`write_bytes` implementation would report every JSON file stale on a fresh Windows checkout and create an infinite check/sync drift loop. Do **not** use `read_bytes`/`write_bytes` or `open(..., newline="")` for the metadata pass.

Both functions continue to return a sorted tuple of absolute paths. The CLI (`python -m cities2_mcp.plugin_packages sync|check`) needs no change and now covers metadata automatically. (A builder exception mid-loop could leave the real tree partially rewritten; acceptable because builders are deterministic pure functions, asserted by `test_metadata_builders_are_deterministic`.)

Adding an `*.json text eol=lf` `.gitattributes` rule is out of scope: the text-I/O comparison above is deterministic across platforms without it; normalizing JSON line endings can be a separate follow-up.

### First-sync normalization

Running `sync` for the first time produces a small, reviewable diff that is committed as part of this change:

- Two JSON files are reformatted (pure whitespace; key order already matches `json.dumps` output everywhere): `integrations/anthropic/claude-plugin/.claude-plugin/plugin.json` (nested `description` keys indented 10 spaces instead of 6) and `plugins/cities2-mcp/.codex-plugin/plugin.json` (`longDescription` indented 2 spaces instead of 4). The other six JSON metadata files round-trip through `json.dumps(indent=2)` byte-for-byte.
- The Codex/shared `README.md` is reflowed from hard-wrapped lines to single-logical-line paragraphs (per `AGENTS.md`), and both READMEs gain the generated-by marker.
- `plugin_metadata.py` (new) and the edited `plugin_packages.py` / `agent_assets.py` get re-vendored into the two `vendor/cities2_mcp/` trees — mechanical churn handled by the existing payload sync.

## Tests: `tests/test_packaging.py`

Keep the existing guardrail tests (`test_anthropic_distribution_artifacts_are_version_aligned`, `test_codex_distribution_artifacts_are_version_aligned`, `test_codex_plugin_package_is_antigravity_plugin`, and the launcher/serve tests). They still pass after regeneration and document the contract. Add:

- `test_repo_metadata_in_sync` — `plugin_packages.check_packages(ROOT)` returns `()` (the committed repo is fully in sync, payloads and metadata).
- A per-file drift test (parametrized over the 10 metadata files) — set up a temp root with the existing skills/`cities2_mcp` payload fixture (`_write_plugin_sync_fixture`, since `sync_packages`/`check_packages` still run the payload pass before the metadata pass), run `sync`, mutate one metadata file, assert `check` reports that file as stale, then `sync` restores it and `check` is clean. (The builders themselves ignore disk, but the public sync/check API copies skills and `cities2_mcp` first, so the corpus fixture is required.)
- `test_generated_metadata_is_valid_and_canonical` — each generated JSON parses as valid JSON. The version-equality check applies only to the four version-bearing JSON artifacts, respecting their shape: the three `plugin.json` files carry a top-level `version` equal to `cities2_mcp.__version__`, and `.claude-plugin/marketplace.json` carries `plugins[0].version` equal to it (the two `.mcp.json` files, `mcp_config.json`, and `.agents/plugins/marketplace.json` have no version field). Other canonical fields are asserted per-artifact only where the field exists: `name` (`NAME`) in the plugin.json/marketplace.json files; `author` in the Codex/Claude `plugin.json` and `.claude-plugin/marketplace.json`; `keywords`/`repository` (`KEYWORDS`/`REPO_URL`) in the Codex/Claude `plugin.json`; and `privacyPolicyURL` (`PRIVACY_URL`) only in the Codex `.codex-plugin/plugin.json` interface.
- `test_metadata_builders_are_deterministic` — calling each builder twice yields identical output.

These satisfy the acceptance criterion that tests cover stale generated metadata, not only stale copied skills/vendor payloads.

## Acceptance criteria mapping

- *`sync` regenerates all intended plugin distro payloads and metadata from canonical sources* → metadata registry + builders driven by `sync_packages`.
- *`check` fails when any generated Claude, Codex, or Antigravity distribution artifact drifts* → metadata pass in `check_packages`, exercised by per-file drift tests.
- *Platform-specific files can still express platform-specific config, user settings, and launch behavior* → `CLAUDE_USER_CONFIG`, `CODEX_INTERFACE`, `ANTIGRAVITY_BOOTSTRAP_JS`, and per-platform builders preserve all current platform differences verbatim.
- *Tests cover stale generated metadata, not only stale copied skills/vendor payloads* → new metadata drift/validity tests.
- *Contributor docs clearly state which files are canonical and which are generated* → CONTRIBUTING.md Canonical vs Generated section.
